You are generating a status report for all feature specs in the sonar-insights project.

## Phase 1 — Read all specs

Read every `.md` file in `specs/`. For each, extract from the YAML frontmatter:
- `spec` — number
- `title`
- `draft-status` — one of: `draft`, `needs-revision`, `ready`
- `impl-status` — one of: `not-started`, `in-progress`, `complete`
- `prerequisites` — list of spec numbers (may be empty)

Also note: any spec without a `draft-status` field should be treated as `ready` (older specs predating the field).

## Phase 2 — Parallelism analysis

For specs that are `ready` and `not-started`, identify which can safely run in parallel.

**Step 1 — Dependency filter**: A spec cannot run in parallel with any spec listed in its `prerequisites` unless that prerequisite is already `complete`. Build a dependency graph.

**Step 2 — File overlap analysis**: For each candidate spec, read its content and identify which packages and files it likely touches. Look for mentions of:
- Package names: `cmd/`, `internal/collector/`, `internal/analyzer/`, `internal/sonarqube/`, `internal/targets/`, etc.
- Specific file names: `collect.go`, `analyze.go`, `run.go`, `root.go`, etc.
- Structural changes: anything that says "refactor", "rename", "replace", "extract" on a shared type or interface

**Step 3 — Group into parallel batches**: Specs that touch entirely different packages with no shared files are safe to run in parallel. Specs that touch overlapping files must be serialized.

Err on the side of caution: if overlap is unclear, mark them as serial.

## Phase 3 — Write STATUS.md

Write the file `specs/STATUS.md` with the following structure:

```markdown
# Spec Status

_Updated: YYYY-MM-DD_

## All specs

| # | Title | Draft | Impl |
|---|-------|-------|------|
| 001 | Title | ready | complete |
| 002 | Title | ready | in-progress |
...

## Implementation queue

### Ready — can start now
Specs with `draft-status: ready` and `impl-status: not-started`, ordered by spec number (lowest first = highest priority).

List each as: `NNN — Title`

If the queue is empty, say "Nothing ready to implement."

### Parallel opportunities
Groups of ready specs that can run simultaneously without risk of conflict.

For each group:
**Group N** (touches: [package list])
- NNN — Title
- NNN — Title

If no parallelism is possible (all ready specs touch overlapping files), say "No safe parallelism identified — implement serially."

### Needs revision — awaiting your input
Specs with `draft-status: needs-revision`. These are blocked on decisions only you can make.

List each as: `NNN — Title`

If none, say "None."

### In progress
Specs with `impl-status: in-progress`.

List each as: `NNN — Title`

If none, say "None."

### Complete
Spec numbers only, comma-separated: `001, 002, 007`

If none, say "None."

---
_Generated by /spec-status_
```

## Phase 4 — Report to the user

After writing `specs/STATUS.md`, print the same content to the conversation so the user can see it immediately without opening the file.

Then add one short paragraph: your recommendation on what to work on next and why (e.g. "Spec 014 (target registry) is the recommended next implementation — it is a prerequisite for 7 other specs and unblocks significant parallelism once complete.").

## Behaviour rules

- Always regenerate `specs/STATUS.md` from scratch — do not append or merge with a previous version.
- If a spec file has malformed or missing frontmatter fields, note it in the report under a "Malformed specs" section rather than silently skipping it.
- Do not modify any spec file. This skill is read-only except for writing `STATUS.md`.
