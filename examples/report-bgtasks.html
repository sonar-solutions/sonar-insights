Introduction

This report presents an analysis of background tasks processed by the SonarQube Server Compute Engine over a specified period. The input data from this report is taken from the output of the GET api/ce/activity REST API endpoint. SonarQube Server keeps this information for up to 180 days.

The SonarQube Server Compute Engine is responsible for executing various background tasks, including project analyses, portfolio recalculations, and project reindexing. The Compute Engine is the most critical component when evaluating SonarQube Server's performance, as it directly impacts analysis throughput, which in turn affects the speed of CI/CD pipelines and how quickly developers receive SonarQube feedback in their DevOps platforms. Starting from the Enterprise Edition, SonarQube Server supports multiple Compute Engine workers, enabling parallel processing of background tasks to significantly improve performance and scalability.

The goal of this report is to provide insights into your SonarQube Server's Compute Engine workload patterns and suggest recommendations for capacity planning and performance optimization. By analyzing historical task data, this report aims to help you evaluate the appropriate number of Compute Engine workers to support your organization's performance requirements and service level objectives.

Note on Timestamps: All date and time values in this report are analyzed and presented in Coordinated Universal Time (UTC). Task submission times, execution windows, and capacity demand calculations are all based on UTC timestamps, ensuring consistent analysis regardless of the SonarQube Server's local timezone configuration or the timezone where this analysis is run.

Capacity Planning Recommendations

The higher the percentile chosen, the more resilient your server will be to short periods of high demand. Lower percentiles (e.g., 90%) provide conservative provisioning suitable for typical workloads with occasional queuing during peaks, while higher percentiles (e.g., 99.9%) ensure very generous provisioning that can handle nearly all demand spikes without delays.

ℹ️ About the Capacity Demand Calculation Methodology (click to expand)

What is Calculated and How

This section of the report estimates Compute Engine capacity demand by dividing the analysis timeline into fixed-length time buckets (aligned to UTC) and calculating the theoretical demand within each bucket. For each background task, the algorithm assumes execution could have started immediately upon submission and distributes its execution time across all buckets that overlap with this theoretical execution window. When a task's execution window spans multiple buckets, the execution time is proportionally allocated based on how much of the window falls within each bucket. The result is a demand value per bucket (measured as accumulated execution time), which is then used to calculate percentiles across all buckets to identify typical and peak capacity requirements.

Why This Approach is Used

The available input data includes submission time, actual execution start time, and actual execution end time for each task, but these timestamps have only 1-second resolution. This limited resolution makes it impossible to accurately reconstruct the historical state of the task queue at any given moment—specifically, which tasks were running in parallel versus which were queued waiting for available workers. By calculating demand from the submission timestamp instead (assuming tasks could execute immediately), the algorithm produces a theoretical upper bound on capacity requirements that is independent of the historical worker configuration.

Performance Considerations Beyond Worker Count

While this section of the report focuses on Compute Engine worker capacity, it is critical to understand that SonarQube Server performance and analysis throughput depend on multiple interrelated factors. An important caveat when interpreting these results: if the SonarQube Server was already experiencing performance problems during the analyzed period (such as database saturation, CPU exhaustion, or memory pressure), the calculated demand values will reflect this degraded state. The database is often the single biggest performance bottleneck in production deployments. Effective capacity planning requires holistic evaluation of all infrastructure components, proper database tuning, and incremental worker scaling with performance validation at each step.
